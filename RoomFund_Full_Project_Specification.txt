ROOMFUND — COMPLETE WEB APP BUILD SPECIFICATION
====================================================

PROJECT NAME
------------
RoomFund

TAGLINE
-------
Shared-room expense management made simple, fair, and transparent.

PROJECT PURPOSE
---------------
Build a production-ready web application for students, roommates, flatmates,
PG residents, couples, families, and other people sharing a rented room/home.

RoomFund must let users manage:

1. Personal expenses
2. Common/shared room expenses
3. Roommate-wise contributions
4. Equal expense splitting
5. Custom/manual expense splitting
6. Who-paid / who-owes calculations
7. Settlements between roommates
8. Daily, weekly, monthly, and yearly expense records
9. Rent and recurring bills
10. Expense categories
11. Room-level financial summaries
12. Personal financial summaries
13. Complete historical records
14. SQLite database persistence
15. Backend/API hosted from GitHub
16. Frontend deployable on Vercel
17. Light mode + dark mode
18. Responsive mobile/tablet/desktop UI
19. Automated tests and database tests
20. Proper validation, error handling, loading states, empty states, and security

IMPORTANT PRODUCT PRINCIPLE
---------------------------
The application must clearly separate:

A. PERSONAL EXPENSE
   Only the selected user is responsible for the expense.

B. COMMON EXPENSE
   The expense belongs to the room/group and can be split among selected
   roommates using equal or custom shares.

C. SETTLEMENT
   A payment made by one roommate to another to clear an outstanding balance.

The application must never silently mix personal and common expenses.

- PostgreSQL-compatible architecture for future production scaling

DATABASE
--------
Development/default:
- SQLite

Database requirements:
- Foreign keys enabled
- Proper indexes
- UUID or secure unique identifiers
- UTC timestamps
- Decimal-safe monetary representation
- Migration support through Alembic
- No business-critical data stored only in frontend/localStorage

REPOSITORIES
------------
Recommended separation:

roomfund-frontend
roomfund-backend

The backend repository must contain the complete API, database models,
migrations, tests, configuration, and deployment configuration.

The frontend repository must contain the complete Next.js application,
UI, API integration, validation, and frontend tests.

VERCEL
------
Deploy the frontend to Vercel.

IMPORTANT:
Do not assume that SQLite stored on a normal ephemeral serverless filesystem
is suitable for permanent production persistence.

For a real production deployment, use a persistent hosted database such as
PostgreSQL, while retaining SQLite compatibility for local development/testing.

If SQLite is specifically required for the first MVP, provide a clearly
documented deployment mode and do not claim that ephemeral Vercel storage
provides permanent SQLite persistence.

====================================================
8. EXPENSE SPLIT METHODS
====================================================

EQUAL SPLIT
-----------
Amount / number of participants.

Example:
₹900 / 3 = ₹300 each.

PERCENTAGE SPLIT
----------------
Example:
Prem 50%
Rahul 30%
Aman 20%

VALIDATION:
Total must equal exactly 100%.

CUSTOM AMOUNT SPLIT
-------------------
Example:
Prem ₹500
Rahul ₹250
Aman ₹150

Total must equal expense amount.

SHARES / UNITS
--------------
Example:
Prem = 2 shares
Rahul = 1 share
Aman = 1 share

₹1,200 / 4 shares = ₹300 per share.

Optional future method:
- Itemized split

====================================================
9. FAIR EXPENSE CALCULATION ENGINE
====================================================

Create a central backend service:

ExpenseSplitService

Input:
- total amount
- payer
- participants
- split method
- split configuration

Output:
- participant share
- amount owed
- amount paid
- net balance
- settlement suggestions

Example:

Total = ₹1,000
Payer = Prem
Participants = Prem, Rahul, Aman

Each share = ₹333.33 except rounding adjustment.

The algorithm must handle currency rounding safely.

Never use floating-point arithmetic for financial calculations.

Use Decimal or integer minor units such as paise.

====================================================
10. BALANCE ENGINE
====================================================

For every room calculate:

total room expenses
total paid by each member
total personal spending
total common spending
member's own share
member's credit
member's debt
net balance

Interpretation:

Positive:
Member should receive money.

Negative:
Member owes money.

Zero:
Settled.

Example:

Prem paid: ₹2,000
Prem's share: ₹800
Net: +₹1,200

Rahul paid: ₹500
Rahul's share: ₹800
Net: -₹300

Aman paid: ₹0
Aman's share: ₹900
Net: -₹900

The dashboard must clearly show:
"You receive"
"You owe"
"Settled"

31. API SECURITY
====================================================

Every protected endpoint must verify:
- authenticated user
- room membership
- correct ownership/role
- resource permissions

Prevent:
- IDOR
- unauthorized room access
- unauthorized expense editing
- mass assignment
- SQL injection
- XSS
- CSRF where applicable
- insecure file upload
- password exposure

Never trust room_id supplied by frontend without authorization checking.

====================================================
32. VALIDATION
====================================================

Amount:
- > 0
- maximum configured value

Split:
- equal split must match total
- percentage must equal 100%
- custom amounts must equal total
- shares must be > 0

Settlement:
- payer != receiver
- amount > 0
- cannot exceed allowed outstanding amount unless explicitly permitted

Dates:
- valid ISO dates
- recurring end date cannot precede start date

Email:
- valid format

Room:
- name required
- reasonable length limits
